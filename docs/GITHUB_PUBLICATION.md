Лицензия авторских материалов — [MIT](../LICENSE). При сборке Vite автоматически формирует `dist/.vite/license.md` с лицензиями включённых зависимостей; [лицензия шрифта](../public/fonts/Unbounded-OFL.txt) поставляется отдельно вместе со шрифтом.

GitHub не требует обязательного набора community-файлов для создания репозитория. Здесь подготовлены README, лицензия, SECURITY, CONTRIBUTING, CODE_OF_CONDUCT, SUPPORT, CITATION, CODEOWNERS, формы Issues, шаблон pull request, CI и Dependabot, чтобы проект было проще использовать и сопровождать.

## Перед открытием доступа

1. Выполните `npm ci` и `npm run check`. Проверьте `npm audit` и текущие уведомления о зависимостях.
2. Просмотрите все публикуемые изменения и историю: не должно быть секретов, личных резервных копий или материалов, на распространение которых нет прав. Для найденного секрета сначала отзовите доступ; удаления файла из последнего коммита недостаточно.
3. Проверьте право использования сторонних брендовых материалов. MIT проекта не заменяет разрешение их владельцев.
4. Проверьте адрес для приватных сообщений в SECURITY и CODE_OF_CONDUCT, автора в LICENSE и CITATION, description и topics репозитория.
5. Закоммитьте проверенные изменения и отправьте их на GitHub. Community-файлы и формы станут доступны после попадания в `main`; изменение локальных файлов само по себе не обновляет GitHub.
6. Для общедоступной публикации откройте Settings → General → Danger Zone → Change repository visibility и выберите Public, ознакомившись с последствиями GitHub. До этого репозиторий доступен только людям с выданными правами; topics не делают приватный проект общедоступным.

## Настройки после публикации

- В Security включите **Private vulnerability reporting**, если настройка доступна, и проверьте кнопку Report a vulnerability. В SECURITY есть резервный канал по почте.
- В Settings → Pages выберите **Source: GitHub Actions**. Workflow `pages.yml` публикует `dist` при push в `main` или ручном запуске после `npm run check`; доступность Pages для приватного репозитория зависит от тарифа GitHub.
- После успешного deploy проверьте адрес из workflow и укажите его как Website в About репозитория. Не указывайте предполагаемый адрес до появления работающей публикации.
- CI `ci.yml` проверяет pull request в `main`, push в `main` и ручные запуски без прав на deploy. Его статус не зависит от настроек GitHub Pages; workflow публикации также проверяет сборку перед deploy.
- Dependabot еженедельно предлагает обновления npm и GitHub Actions. Обновления применяются после проверки; локальный патч `braces` обслуживается по `vendor/braces/README.md`.
- При необходимости включите правило защиты `main` с обязательным CI и запретом force push. Наличие CODEOWNERS назначает владельца для review, но само по себе не требует его одобрения.

## Релизы и обнаружение

Используйте только topics, которые отражают реальное содержание проекта. В description полезно назвать независимый характер проекта, язык, экзамен, число вопросов и формат практики. Темы не гарантируют позицию в поиске.

Теги версий и GitHub Releases создавайте для проверенных выпусков с описанием изменений. `dist` остаётся вне Git; при упаковке готовой сборки для релиза приложите корневой [LICENSE](../LICENSE), сохраните сгенерированный `.vite/license.md` и лицензии шрифтов. Дату и версию выпуска в CITATION.cff добавляйте после фактического релиза.

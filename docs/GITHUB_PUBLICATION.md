# Публикация проекта: инструкция для владельца

Здесь собраны инструкции по публикации репозитория и сайта, а также настройке GitHub. Это памятка для владельца проекта.

Репозиторий: [ed-would/yandex-ai-studio-exam-lab](https://github.com/ed-would/yandex-ai-studio-exam-lab). Автор: [Ed Would](https://github.com/ed-would). Лицензия авторских материалов – [MIT](../LICENSE). При сборке Vite автоматически формирует `dist/.vite/license.md` с лицензиями включённых зависимостей; [лицензия шрифта](../public/fonts/Unbounded-OFL.txt) поставляется отдельно вместе со шрифтом.

GitHub не требует обязательного набора community-файлов для создания репозитория. Здесь подготовлены README, лицензия, SECURITY, CONTRIBUTING, CODE_OF_CONDUCT, SUPPORT, CITATION, CODEOWNERS, формы Issues, шаблон pull request и CI, чтобы проект было проще использовать и сопровождать.

## Перед открытием доступа

1. Выполните `npm ci` и `npm run check`. Проверьте `npm audit` и текущие уведомления о зависимостях.
2. Просмотрите все публикуемые изменения и историю: не должно быть секретов, личных резервных копий или материалов, на распространение которых нет прав. Для найденного секрета сначала отзовите доступ; удаления файла из последнего коммита недостаточно.
3. Проверьте право использования сторонних брендовых материалов. MIT проекта не заменяет разрешение их владельцев.
4. Проверьте адрес для приватных сообщений в SECURITY и CODE_OF_CONDUCT, автора в LICENSE и CITATION, description и topics репозитория.
5. Закоммитьте проверенные изменения и отправьте их на GitHub. Community-файлы и формы станут доступны после попадания в `main`; изменение локальных файлов само по себе не обновляет GitHub.
6. Для общедоступной публикации откройте Settings → General → Danger Zone → Change repository visibility и выберите Public, ознакомившись с последствиями GitHub. До этого репозиторий доступен только людям с выданными правами; topics не делают приватный проект общедоступным.

## Ручная проверка перед релизом

Проверить код локально можно командой `npm run check`; GitHub Actions для неё не нужны. Чтобы вручную запустить workflow в GitHub, установите и авторизуйте GitHub CLI (`gh`) с доступом на запись в репозиторий.

1. Выполните `npm run ci:dispatch`. Команда отправит CI для ветки `main`; дождитесь успешного завершения в Actions.
2. После успешной проверки выполните `npm run pages:dispatch`, чтобы опубликовать сайт.
3. Обе команды только ставят workflow в очередь. Список запусков смотрите командой `gh run list --workflow ci.yml`; отдельный запуск можно отслеживать через `gh run watch RUN_ID`.

## Публикация сайта на GitHub Pages

В репозитории есть [workflow публикации](../.github/workflows/pages.yml). Он устанавливает зависимости, выполняет `npm run check`, загружает `dist` и публикует сайт.

1. Поместите содержимое проекта в корень GitHub-репозитория: `package.json` и `.github` должны находиться в корне. Не добавляйте `node_modules` или `dist`.
2. Откройте **Settings → Pages → Build and deployment → Source → GitHub Actions**.
3. Отправьте изменения в `main`, затем запустите `npm run pages:dispatch`.
4. Дождитесь успешного завершения. Адрес сайта появится в Pages и результате задания публикации.

Если основная ветка называется иначе, замените `--ref main` на её имя в scripts `ci:dispatch` и `pages:dispatch`. Если Actions запрещены настройками репозитория или организации, потребуется разрешить их. Доступность Pages для приватного репозитория зависит от тарифа GitHub.

В Vite задано `base: './'`: имя репозитория не нужно вписывать в код. Приложение может находиться в корне домена или подпапке; пользователю опубликованного тренажёра не нужен аккаунт GitHub. При смене адреса прогресс переносится через JSON.

Архив исходников не содержит `dist` и `node_modules`. Сборку создаёт `npm run build` или workflow. Успешная локальная сборка сама по себе не доказывает публикацию конкретного сайта.

Для публикации на другом статическом хостинге разместите содержимое `dist` на хостинге. `npm run preview` предназначен для локальной проверки.

## Настройки после публикации

- В Security включите **Private vulnerability reporting**, если настройка доступна, и проверьте кнопку Report a vulnerability. В SECURITY есть резервный канал по почте.
- После успешного deploy проверьте адрес из workflow и укажите его как Website в About репозитория. Не указывайте предполагаемый адрес до появления работающей публикации.
- CI `ci.yml` и публикация Pages запускаются только вручную. Оба workflow выполняют `npm run check`; CI не имеет прав на deploy.

- Обновления зависимостей проверяются вручную; локальный патч `braces` обслуживается по `vendor/braces/README.md`.
- При необходимости включите правило защиты `main` с обязательным CI и запретом force push. Наличие CODEOWNERS назначает владельца для review, но само по себе не требует его одобрения.

## Social preview репозитория

Единственный рабочий файл обложки находится в [`public/social-preview.jpg`](../public/social-preview.jpg). Он публикуется с сайтом как `social-preview.jpg` и указан в мета-тегах `index.html`, чтобы превью появлялось при отправке ссылки на сайт. Для загрузки в настройки репозитория используйте этот же файл. Отдельный дубль в дизайн-лабе не хранится; прежняя версия сохранена в архиве. Загрузка в настройки репозитория сама по себе обложку GitHub не включает. Файл имеет формат JPEG, размер 1280 × 640 px и вес 197 799 байт.

GitHub принимает PNG, JPG и GIF размером меньше 1 MB. Рекомендуемый минимум: 640 × 320 px, а размер 1280 × 640 px даёт лучшее отображение. Итоговый JPEG соответствует этим требованиям. Источник: [официальная документация GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/customizing-your-repositorys-social-media-preview).

Чтобы загрузить его, откройте **Settings → Social preview → Edit → Upload an image…**. Обложка не активируется от одного наличия файла в репозитории. Сейчас файл подготовлен локально, настройка GitHub не менялась.

## Релизы и обнаружение

Используйте только topics, которые отражают реальное содержание проекта. В description полезно назвать независимый характер проекта, язык, экзамен, число вопросов и формат практики. Темы не гарантируют позицию в поиске.

Теги версий и GitHub Releases создавайте для проверенных выпусков с описанием изменений. `dist` остаётся вне Git; при упаковке готовой сборки для релиза приложите корневой [LICENSE](../LICENSE), сохраните сгенерированный `.vite/license.md` и лицензии шрифтов. Дату и версию выпуска в CITATION.cff добавляйте после фактического релиза.
